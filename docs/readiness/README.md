# otelc v1 readiness review — findings, reproductions, and benchmarks vs orchestrion

Scope: pre-v1 audit of open-telemetry/opentelemetry-go-compile-instrumentation (main @ 73f867f, 2026-07-07), cross-checked against orchestrion v1.11.0's capabilities and dd-trace-go v2.9.1. Every claim below was reproduced with runnable scripts; logs live in `evidence/`. "Blocker" is used strictly for decisions that could only be corrected later by breaking users.

This directory carries the review as a standalone record: `evidence/` holds the raw reproduction logs and the ten individual findings (`evidence/findings/`), `benchmarks.md` holds the orchestrion comparison and its methodology caveats, and `../adr/0006-*.md` / `../adr/0007-*.md` are two draft ADRs this review produced for decisions that need the SIG's sign-off before the tag.

This document was updated after the initial pass to reflect fixes drafted in response to it; see the status notes inline and in each finding. **Statuses last re-checked against upstream main `ad45522` (2026-07-09)**, after upstream merged #655 (`otelc pin`) and #654 (config/troubleshooting guides): finding 02 is now fixed upstream (re-verified, see its status note), finding 10 was re-verified still present and its framing sharpened, and the drafted fixes now live as fork draft PRs [kakkoyun#9–#15](https://github.com/kakkoyun/opentelemetry-go-compile-instrumentation/pulls) linked per finding. Original reproduction claims remain as tested at 73f867f.

## Bottom line

The instrumentation engine is in good shape: trampoline generation, the seven rule types, golden tests, multi-OS CI, and the version-matrix/latest-lib regression harnesses are real strengths, and the benchmark numbers are already competitive with orchestrion (warm builds slightly faster, runtime overhead at parity). The risk is not the engine — it's the orchestration shell around it (cache identity, go.mod mutation, process lifecycle) and a handful of defaults that become contracts at v1. Four items need a decision or fix before the tag because they are compat-irreversible; seven are serious correctness bugs that can technically be fixed in v1.x without breaking anyone, but three of them (cache staleness, go test, PGO) fail silently, which argues for fixing them before first impressions form. Of those seven, one (rules-vs-tidy) is now fixed upstream by the merged `otelc pin` work, and fixes for five more are up as fork draft PRs; see the table below.

## Compat-critical: decide before the tag (true v1 blockers)

**1. Rule schema freeze vs implementation drift.** docs/rules.md promises `where`-level combinators "at any position" (line 111 at the audited commit; the same doc's `where.file` section separately discloses "not yet supported", i.e. it self-contradicts — re-verified still true at `ad45522`); the loader rejects them (`rule "combinator_rule" has no recognised selector`; underlying: field-presence type inference [#546](https://github.com/open-telemetry/opentelemetry-go-compile-instrumentation/issues/546) + `filter.go:185-199` "not yet supported"). `has_directive` similarly documented-but-rejected. [#164](https://github.com/open-telemetry/opentelemetry-go-compile-instrumentation/issues/164) marks OP4.1–4.3 done — true only for `where.file`. Freezing the schema in this state guarantees breaking either docs-compliant users or the schema later. Implement or de-document before v1. → [finding 10](evidence/findings/10-rules-docs-vs-impl.md); this is the blocking dependency called out in draft [ADR-0007](../adr/0007-v1-compatibility-surface.md).

**2. Distribution/config model.** The documented onboarding (`otel.instrumentation.go` importing `go.opentelemetry.io/otelc/instrumentation/...`) cannot work outside this repo: the modules are unpublished (every build log shows `v0.0.0-00010101000000-000000000000` pseudo-versions and the `sync.go:158` replace hack), the 25 nested modules under `instrumentation/` (23) and `pkg/` (2) are never tagged, and tool files resolve imports before replaces exist. The hook-import restriction plus the embedded bundle also closes the door on third-party instrumentation packages — the orchestrion capability dd-trace-go's migration depends on. [#567](https://github.com/open-telemetry/opentelemetry-go-compile-instrumentation/issues/567) and [#585](https://github.com/open-telemetry/opentelemetry-go-compile-instrumentation/issues/585) are correctly on the roadmap, and [PR #655](https://github.com/open-telemetry/opentelemetry-go-compile-instrumentation/pull/655) (adds the `otelc pin` command #567 describes) **merged 2026-07-08** (`238f23d`) — `otelc pin` is now part of the CLI surface that freezes at the tag. The point for v1 stands: `HookContext`, the tool-file convention, and module paths freeze at the tag, so the extension path must be designed (not necessarily implemented) before it. → feeds #567/#585 and draft [ADR-0007](../adr/0007-v1-compatibility-surface.md).

**3. Telemetry defaults.** Reproduced: traces are silently OFF unless `OTEL_EXPORTER_OTLP_ENDPOINT`/`..._TRACES_ENDPOINT` is set (`OTEL_TRACES_EXPORTER=console` alone emits nothing, contradicting the tool's own docs); metrics export unconditionally (hello-world dials localhost:4318); `OTEL_SDK_DISABLED` is ignored (spec deviation, and contradicts `pkg/runtime/otel_setup.go`'s own doc comment); injected init overwrites the app's own global providers. These are exactly the kind of observable defaults that freeze at v1. → [finding 08](evidence/findings/08-telemetry-defaults.md); no fix in progress and no ADR drafted for this one yet.

**4. Dependency policy + minimum Go.** Every build injects ~45 modules (grpc v1.82, prometheus, x/net, full exporter suite) into the user's module graph; tidy silently upgrades user-pinned versions (warning only); the shipped binary's dependency set diverges from the committed go.mod (SBOM/govulncheck blind spot); embedded modules impose Go >= 1.25 on all target apps while Go 1.24 is still supported upstream. Whichever policy v1 ships becomes the contract. → [finding 03](evidence/findings/03-silent-dependency-injection.md), feeds draft [ADR-0006](../adr/0006-dependency-version-policy-for-bundled-instrumentation.md).

## Benchmarks vs orchestrion (goal: faster and more solid)

Small net/http app, 4-core Linux container, go1.25.0; otelc @73f867f vs orchestrion v1.11.0 + dd-trace-go v2.9.1 (net/http contrib); noop export pipelines on both sides; min-of-runs reported for runtime metrics, full data and methodology caveats in [benchmarks.md](benchmarks.md).

| Metric | plain | otelc | orchestrion |
|---|---|---|---|
| Cold build | 10.7s | 26.1s (2.4x) | 23.4s (2.2x) |
| Warm rebuild (touch main.go) | 0.09s | **2.3s** | 2.8s |
| Binary size | 8.9MB | 25.2MB | 23.7MB |
| Goroutine spawn | 469 ns/op | 468 ns/op | 461 ns/op |
| HTTP round-trip | 81.5µs | 95.7µs (+17%) | 94.6µs (+16%) |

Read: runtime overhead is at parity (goroutine-creation GLS hook is not measurable — good); warm builds are already slightly faster than orchestrion; cold builds are ~12% slower, and otelc's ~2.3s fixed warm-build cost is dominated by the per-build setup phase (`go build -a -x -n` dry run + bundle extract + `go mod tidy`) — the clearest optimization target for the "faster than orchestrion" goal. Binary size carries ~1.5MB over orchestrion from always linking every exporter via autoexport (also flagged in [finding 03](evidence/findings/03-silent-dependency-injection.md)). [benchmarks.md](benchmarks.md) spells out several methodology caveats, including that otelc's "noop" side of the runtime comparison relies on the same off-by-default trace behavior flagged as an open decision in [finding 08](evidence/findings/08-telemetry-defaults.md), not an explicit disable flag — worth knowing before treating these numbers as an SLO baseline (tracked in [#570](https://github.com/open-telemetry/opentelemetry-go-compile-instrumentation/issues/570)).

## Refuted / softened during verification

- "CI is single-platform" — false: ubuntu amd64/arm64, macos, windows all covered. The gap is Go versions, not platforms.
- "docs promise an `otelc pin` command" — false: docs describe the tool-file flow, which is implemented (reading an existing `otel.instrumentation.go`, merged as [#612](https://github.com/open-telemetry/opentelemetry-go-compile-instrumentation/pull/612)); the unpublished-modules problem is what breaks it, not a missing command. The `otelc pin` command itself — which would scaffold/edit that file — is proposed in [PR #655](https://github.com/open-telemetry/opentelemetry-go-compile-instrumentation/pull/655), open and not yet merged.
- "GOPROXY=off always fails" — only when the module cache lacks otelc's deps (i.e., real CI); warm dev machines mask it. [PR #616](https://github.com/open-telemetry/opentelemetry-go-compile-instrumentation/pull/616) (open) adds vendoring support, a narrower, related fix — see [finding 09](evidence/findings/09-goproxy-off.md).
- Windows path handling and bundle extraction (zip-slip) were checked and are fine.
- Two more upstream PRs touch areas this review looked at but aren't reflected as fixes above because they address different gaps than the ones reproduced here: [PR #657](https://github.com/open-telemetry/opentelemetry-go-compile-instrumentation/pull/657) fixes `otelc go build -C <dir>` not honoring the directory flag ([#507](https://github.com/open-telemetry/opentelemetry-go-compile-instrumentation/issues/507)), and [PR #469](https://github.com/open-telemetry/opentelemetry-go-compile-instrumentation/pull/469) adds `//otelc:ignore` / `//otelc:instrument` source directives for opting individual functions or files out of (or back into) instrumentation without a rebuild, mirroring orchestrion's `//orchestrion:ignore`. Both are open, not yet merged, and neither was part of the original reproduction set.

## ADRs

1. **Build-cache identity**: no ADR drafted. A direct fix is in progress instead ([finding 01](evidence/findings/01-build-cache-staleness.md), branch `v1-readiness/cache-identity`) rather than a design decision with real alternatives; the SIG could still write up the `-V=full` stamping approach as a record after the fact if it wants the design citable, but it doesn't block the tag the way the two drafted below do.
2. **Dependency-version policy**: drafted as [ADR-0006](../adr/0006-dependency-version-policy-for-bundled-instrumentation.md) (status: draft/proposed). Presents four options — version-gating bundled rules per ADR-0004, re-matching after dependency sync, failing instead of silently bumping user-pinned versions, and splitting `pkg/runtime`'s exporter tree — with consequences per option and no recommended winner beyond noting that the re-match mechanism fix is already underway upstream.
3. **v1 compatibility surface**: drafted as [ADR-0007](../adr/0007-v1-compatibility-surface.md) (status: draft/proposed). Lists what freezes (`HookContext`, rule schema pending finding 10's resolution, CLI verbs, `OTELC_*` env vars, the tool-file convention) and what's explicitly internal (`matched.json`, `state.json`, `.otelc-build` layout, embedded bundle format, `added_imports` files).
4. **SDK injection defaults**: no ADR drafted in this batch. Would resolve [finding 08](evidence/findings/08-telemetry-defaults.md) as a recorded decision (spec-compliant defaults, kill switch, coexistence with app-configured SDKs) — still open and still needs one.
